A **workspace** is one materialized ref: a git worktree, a port allocation, a
private data directory, and the state entry that ties them together.

`testlane` owns one **bare, partial clone** per project and creates one **git
worktree** per ref. That is the whole model, and most of its behaviour — good
and awkward — follows from it.

## Why worktrees

A worktree gives you a real, separate directory that shares object storage with
one clone. So you can:

- Hold five branches open at once without five full clones on disk.
- Leave your main checkout alone — no stashing to review someone else's branch.
- Run several dev servers at the same time, each on its own port.

## Port isolation

Each workspace gets a contiguous block of ports, sized by the project's `ports`
key (1–10, default 1). The first is exported as `$TESTLANE_PORT` and interpolated as
`{port}`; the rest are `$TESTLANE_PORT_1`, `$TESTLANE_PORT_2`, … and `{port+1}`,
`{port+2}`, ….

```toml [~/.testlane/my-project.toml]
ports = 2

[env]
PORT = "{port}"
API_PORT = "{port+1}"
```

Allocation is deterministic first — the slug is hashed into a window above
`base_port`, and `testlane` only scans upward if that block is taken or occupied. In
practice a given branch keeps the same port across sessions.

See [Run dev servers in parallel](/docs/guides/run-dev-servers-in-parallel) for
the working setup.

## The data directory

Every workspace gets `$TESTLANE_DATA_DIR` — a private directory outside the worktree
at `{worktrees_path}/.data/<slug>`. Use it for things that must not pollute the
git tree: SQLite files, upload directories, caches.

```toml [~/.testlane/my-project.toml]
[env]
DATABASE_URL = "file:{data_dir}/dev.db"
```

## Known caveats

These are consequences of the worktree model, not bugs `testlane` can paper over.
Knowing them saves an afternoon.

::note{title="`.git` is a file, not a directory"}
Inside a worktree, `.git` is a file pointing back at the primary repo. Tooling
that assumes a `.git` directory — some Docker volume setups, older shell
scripts — can trip on this.
::

::note{title="`core.hooksPath` and husky"}
Repositories that configure relative hook paths (husky does) may resolve them
incorrectly from a worktree, and `pnpm install` can try to install hooks into
the bare repo. `testlane doctor` warns when `core.hooksPath` is set. It does not
modify your repository.
::

::note{title="Partial clones fetch lazily"}
The first checkout of a worktree, and a `diff` across not-yet-fetched trees,
need network access. Offline use is degraded by design — the trade for not
downloading history you will never read.
::

::note{title="A branch can only be checked out once"}
Git refuses to check out the same branch in two worktrees. `testlane` detects this
and points you at the existing workspace instead of failing obscurely.
::

::caution{title="Deleting a worktree by hand leaves metadata behind"}
`rm -rf`-ing a workspace directory leaves git's worktree metadata and `testlane`'s
state entry orphaned. `list` then reports the workspace as `missing`, and
`testlane doctor` warns about the drift:

```
SLUG        KIND    BRANCH      STATUS   PORT  AGE  LAST USED
feat-login  branch  feat/login  missing  3053  2m   1m
```

Reconcile with:

```bash
testlane my-project clean --prune-state --yes
```
::

## Inspecting workspaces

```bash
testlane my-project list                 # all workspaces for a project
testlane my-project list --du            # add a disk-usage column
testlane my-project feat/login info      # one workspace in detail
testlane my-project feat/login info --du
```

```
slug: feat-login
kind: branch
ref: feat/login
branch: feat/login
path: ~/dev/testlane/my-project/trees/feat-login
ports: 3053
status: clean
created: 2026-07-25T05:51:38.363Z
last used: 2026-07-25T05:51:38.827Z
```

Both accept `--json` for scripting. See
[Script with Testlane](/docs/guides/script-with-testlane).

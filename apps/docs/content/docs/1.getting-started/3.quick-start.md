By the end of this page you will have a configured project, a materialized
workspace, a command running inside it, and a clean machine again. It takes
about ten minutes.

You need `testlane` [installed](/docs/getting-started/installation) and a git
repository you can clone.

::steps{level="2"}

## Scaffold your first project

`testlane setup` creates the config directory (`~/.testlane` by default), sets a base
`root` for repos and worktrees, and writes your first project file. On a
terminal it prompts for each field; every prompt is also a flag, so the same
command runs unattended.

:::code-group

```bash [interactive]
testlane setup
```

```bash [non-interactive]
testlane setup --name my-project --repo git@github.com:my-org/my-project.git --yes
```

:::

Not sure what it will write? `--dry-run` prints the plan and changes nothing:

```bash
testlane setup --name my-project --repo git@github.com:my-org/my-project.git --dry-run --yes
```

```
mkdir -p /home/you/.testlane
write /home/you/.testlane/defaults.toml
  root = "~/dev/testlane"
write /home/you/.testlane/my-project.toml
  repo = "git@github.com:my-org/my-project.git"
```

The plan prints the config directory expanded, so you see your real home
directory rather than `~`.

## Teach the project how to run

`setup` writes the minimum. Open the project file and add the two things `testlane`
needs to make a workspace runnable — how to install dependencies, and what your
commands are:

```bash
testlane config edit my-project
```

```toml [~/.testlane/my-project.toml]
repo = "git@github.com:my-org/my-project.git"
editor = "code"

[setup]
run = "pnpm install --frozen-lockfile"
cache_key = ["pnpm-lock.yaml"]

[env]
PORT = "{port}"

[commands.dev]
run = "pnpm dev"
```

`{port}` is a [template variable](/docs/configuration/environment-and-templates).
Each workspace gets its own port, so two dev servers never collide.

:::note
`repo_path` and `worktrees_path` are left out on purpose — they default to
`{root}/{project}/repo` and `{root}/{project}/trees`. See
[Configuration](/docs/configuration/overview).
:::

## Check your environment

`doctor` inspects your tools, your config directory, and every project you have
configured. Run it before you trust a setup:

```bash
testlane doctor
```

```
OK   git version: git 2.50.1
OK   gh (github cli): authenticated
OK   config dir: ~/.testlane
OK   state dir: ~/.local/state/testlane
OK   project my-project: config: schema-valid
OK   project my-project: repo: bare repo at ~/dev/testlane/my-project/repo
OK   project my-project: fetch refspec: remote.origin.fetch configured
```

`doctor` exits non-zero if any check fails, so it works in CI. To validate only
the config files, use `testlane config validate`.

## Materialize a workspace

Now the pipeline. Pick any ref — a branch name, a PR number, a full commit SHA:

```bash
testlane my-project feat/login checkout
```

```
→ cloning git@github.com:my-org/my-project.git (bare, partial)
→ fetching origin/feat/login
→ worktree ready: ~/dev/testlane/my-project/trees/feat-login
~/dev/testlane/my-project/trees/feat-login
```

The first run clones once. Every later ref reuses that bare repo, so the second
workspace is fast.

`checkout` prints the worktree path on stdout and nothing else, which makes it
the scriptable primitive:

```bash
cd "$(testlane my-project feat/login checkout)"
```

## Do something in it

`run` materializes the workspace, executes `[setup]`, then runs a configured
command inside the worktree:

```bash
testlane my-project feat/login run dev
```

```
→ worktree ready (reused)
→ running setup
...
listening on 3053
```

Other ways to act on the same workspace:

```bash
testlane my-project feat/login code               # open it in your editor
testlane my-project feat/login shell              # interactive shell, testlane env exported
testlane my-project feat/login exec -- git log --oneline -2
testlane my-project feat/login diff --stat
```

## See what you have

```bash
testlane my-project list
```

```
SLUG        KIND    BRANCH      STATUS  PORT  AGE  LAST USED
feat-login  branch  feat/login  clean   3053  0m   0m
```

On a terminal, a bare `testlane my-project` turns that list into a picker and prints
the chosen path — so `cd "$(testlane my-project)"` walks you into a workspace.

## Clean up

```bash
testlane my-project clean --all --yes
```

```
→ plan:
  feat-login (clean, 16 KB)
feat-login
→ freed 16 KB
```

`clean` prints its plan and asks for confirmation first; `--yes` skips the
prompt. In day-to-day use you will reach for the filters instead —
`--merged`, `--closed`, `--older-than 7d`. See
[cleaning up workspaces](/docs/guides/clean-up-workspaces).

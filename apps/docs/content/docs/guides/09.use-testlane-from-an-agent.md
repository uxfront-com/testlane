An AI coding agent can review a pull request the way you do: check it out, start
it, open the URL, read the logs, then stop it and clean up. It needs to know which
commands to call and which fields to read, though. Without that, an agent guesses.
Think of an agent that calls `shell` and waits forever for someone to type, one
that runs a dev server with `run` and never gets its prompt back, or one that
parses the progress lines on stderr instead of the JSON on stdout.

By the end of this guide, your agent can drive the whole loop on its own, and
you'll have a short block to paste into `AGENTS.md` or `CLAUDE.md`. You'll need
Testlane installed and at least one project configured, which
[Installation](/docs/uxd/getting-started/installation) and
[Quick start](/docs/uxd/getting-started/quick-start) cover.

The examples use a project called `demo-app` with a `dev` command, and show real
output. Your paths, ports and PIDs will differ. Testlane prints each JSON result
on one line, and we've wrapped them here so they're easier to read.

## Three rules for agents

Let's start with the rules that every step below relies on:

- **Read data from stdout, and only from stdout.** Progress (`→ …`), warnings and
  errors go to stderr, so stdout holds the result and nothing else.
  [Script with uxd](/docs/uxd/guides/script-with-uxd) explains this contract.
- **Always name the verb.** `testlane demo-app 42` with no verb runs the project's
  `default_command`, which is `code` unless the project or `defaults.toml` sets
  another, so it opens an editor.
- **Check the exit code before you read stdout.** When a command in this guide
  fails, it exits non-zero and prints nothing on stdout. [Handle a failure](#handle-a-failure)
  says what to do next.

## Drive a workspace, step by step

### 1. List the projects

```bash
testlane projects --json
```

```json
[
  {
    "name": "demo-app",
    "repo": "git@github.com:my-org/demo-app.git",
    "workspaces": 0,
    "pathExists": false
  }
]
```

`name` is what every other command takes as `<project>`. `workspaces` counts the
workspaces Testlane has checked out for it, and `pathExists` is `false` until the
first checkout clones the repository. An empty array means no project is
configured, so ask the user to add one rather than writing a config file
yourself.

### 2. Check out a ref and get its path

A ref is a PR number (`42`), a branch name (`feat/login`) or a full 40-character
commit SHA. [Refs](/docs/uxd/getting-started/refs) lists every form.

```bash
testlane demo-app feat/login checkout --json
```

```json
{
  "project": "demo-app",
  "slug": "feat-login",
  "ref": "feat/login",
  "kind": "branch",
  "branch": "feat/login",
  "path": "/home/you/dev/testlane/demo-app/trees/feat-login",
  "ports": [3053],
  "created": true
}
```

`path` is the absolute path of the workspace, so run your own commands there.
`created` is `false` when the workspace already existed, and the command is safe
to repeat. For a PR, `kind` is `"pr"` and `branch` is `"pr/42"`.

Note that `checkout` skips the project's `[setup]`, like installing dependencies,
unless you add `--setup`. `start` runs it for you.

### 3. Start a command and get its URL

```bash
testlane demo-app feat/login start dev --json
```

```json
{
  "project": "demo-app",
  "slug": "feat-login",
  "command": "dev",
  "pid": 92193,
  "port": 3053,
  "url": "http://127.0.0.1:3053",
  "log": "/home/you/dev/testlane/demo-app/trees/.data/feat-login/process.log",
  "startedAt": "2026-11-13T10:40:13.565Z",
  "reused": false
}
```

`start` checks out the ref if it isn't already, runs `[setup]`, starts the
command in the background and returns once `url` accepts connections. The process
keeps running after `start` exits. `dev` must be a name under `[commands]` in the
project's config.

Keep in mind that `start` can take minutes, since `[setup]` usually installs
dependencies first. After setup, it waits up to 300 seconds for the port, and
`--timeout <seconds>` changes that wait. Give your own tool call enough time.

`start` is safe to repeat. When the same command is already running, it prints
the same object with `"reused": true`.

### 4. Check what's running

```bash
testlane demo-app ps --json
```

```json
[
  {
    "slug": "feat-login",
    "command": "dev",
    "pid": 92193,
    "port": 3053,
    "status": "running",
    "startedAt": "2026-11-13T10:40:13.565Z",
    "log": "/home/you/dev/testlane/demo-app/trees/.data/feat-login/process.log"
  }
]
```

`ps` takes the project only, with no ref, and lists every process `start` left
in it. `status` is `running`, or `exited` when the process died on its own, like
after a crash. With nothing started, it prints `[]`.

### 5. Read the logs

`logs` has no `--json`. It prints the process's log on stdout, as it is:

```bash
testlane demo-app feat/login logs
```

```
listening on 3053
```

The log keeps growing while the process runs, so we recommend reading only its
end, like `testlane demo-app feat/login logs | tail -n 50`. Never pass `-f` or
`--follow`: they keep printing until someone interrupts them, so your call never
returns. With no log yet, `logs` exits `2`.

### 6. Stop the process

`stop` has no `--json`. Read its exit code, which is `0` whether or not anything
was running:

```bash
testlane demo-app feat/login stop
```

stderr says what happened, either `→ dev stopped (pid 92193)` or
`→ not running: demo-app/feat-login`. The log stays, so you can still read it
after `stop`.

### 7. Remove the workspace

`rm` has no `--json`, and it asks for confirmation, so pass `--yes`:

```bash
testlane demo-app feat/login rm --yes
```

```
feat-login
```

stdout names each slug it removed. `rm` stops a running process first, so you
don't need `stop` before it. Without `--yes`, `rm` exits `2` instead of waiting
for an answer.

`rm` keeps a workspace with uncommitted changes. It exits `0`, prints nothing on
stdout and warns on stderr:

```
warning: skipping feat-login: worktree is dirty (use --force)
```

So check that stdout names the slug. `--force` removes the workspace anyway and
throws those changes away, and for a branch workspace it also deletes the local
branch, so ask the user before you add it.

## Handle a failure

Testlane exits `0` on success. Any other code means the command failed, and
stderr ends with one `error(E_…)` line and sometimes a `hint:` line:

```
error(E_SETUP): 'dev' exited before 127.0.0.1:3064 accepted connections
hint: full log: /home/you/dev/testlane/demo-app/trees/.data/pr-42/process.log
```

Report both lines to the user, and don't retry the same command unchanged, since
it usually fails the same way. This is what each code usually asks of an agent:

| Code | Name | What to do |
|---|---|---|
| `1` | `E_INTERNAL` | Stop and report it, since it's a bug in Testlane |
| `2` | `E_USAGE` | Fix the command, like a missing `--yes` or a command name that isn't configured |
| `3` | `E_CONFIG` | Report it, and leave fixing the config to the user |
| `4` | `E_RESOLVE` | Check the ref, then ask the user which one they meant |
| `5` | `E_GIT` | Report it, since a `git` or `gh` command failed |
| `6` | `E_SETUP` | Read the lines above the error and `logs`, then report what failed |

[Exit codes](/docs/uxd/cli/exit-codes) is the full reference.

A few cases come up often. `start` exits `2` when another command already runs in
that workspace, and its hint names the `stop` to run first. It exits `6` when the
command exits before its port is ready, when the port isn't ready within
`--timeout`, or when something else already holds the port. In each case it
leaves no process behind.

## Commands an agent must not call

These commands open something for a person and wait for them, so an agent's call
never returns:

- **`shell`** starts an interactive shell in the workspace. Run your commands in
  the `path` from `checkout` instead, or use `exec`, like
  `testlane demo-app 42 exec -- npm test`.
- **`code`** opens the workspace in an editor. With a terminal editor like `vim`,
  it waits until someone closes it. Open `path` with your own tools.
- **`config edit`** and **`config add`** open a project's config file in an
  editor. `add` is another name for `edit`. Leave config changes to the user.

Two more need care. `run` waits until its command exits, which is right for
`run test` and wrong for a dev server, so use `start` for anything that keeps
running. And bare `testlane <project>` opens a picker that waits for a choice
when it runs in a terminal, so use `testlane <project> list --json` to list
workspaces.

## Paste this into AGENTS.md or CLAUDE.md

Copy this block into the instructions file your agent reads:

```md
## Testlane

Testlane checks out a ref of a project into its own workspace and runs it.
Always name the verb, read results from stdout and check the exit code first.

- List projects: `testlane projects --json`. Use a `name` as `<project>`.
- Check out a ref (PR number, branch or full SHA):
  `testlane <project> <ref> checkout --json`. Work in its `path`.
- Start a server: `testlane <project> <ref> start <command> --json`.
  Open its `url`. It can take minutes, since it installs dependencies first.
- See what runs: `testlane <project> ps --json`. `status` is `running` or `exited`.
- Read logs: `testlane <project> <ref> logs | tail -n 50`.
  Never pass `-f` or `--follow`.
- Stop: `testlane <project> <ref> stop`.
- Remove: `testlane <project> <ref> rm --yes`. stdout names each removed slug.
  Empty stdout means it kept a workspace with uncommitted changes.
  Ask the user before you add `--force`, which throws them away.

Never run these, since they wait for a person or never return:
- `testlane <project> <ref>` with no verb, which opens an editor by default
- `shell`, `code`, `config edit` or `config add`
- `run` for a server (use `start`), or bare `testlane <project>`

When a command exits non-zero, stop and report its `error(E_…)` and `hint:`
lines from stderr. Don't retry it unchanged. Codes: 1 internal, 2 usage,
3 config, 4 ref, 5 git, 6 setup or start.
Don't edit Testlane's config files unless the user asks.
```

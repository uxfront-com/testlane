## Named commands

Anything under `[commands]` becomes a `run` target.

```toml [~/.testlane/my-project.toml]
[commands.dev]
run = "pnpm dev"
cwd = "packages/app"

[commands.dev.env]
NODE_OPTIONS = "--max-old-space-size=8192"

[commands.test]
run = "pnpm test"
```

```bash
testlane my-project 42 run dev
testlane my-project 42 run test -- --watch
```

| Key | Type | Meaning |
|---|---|---|
| `run` | string | **required** — the command, templated, executed through a shell |
| `cwd` | string | Optional, relative to the worktree root |
| `env` | table | Optional, merged over the project's `[env]` for this command only |

Arguments after `--` are appended to `run`, so `run test -- --watch` executes
`pnpm test --watch`.

::note{title="Built-in verbs win"}
If you name a command after a built-in verb, like `sync`, `info` or `start`,
the built-in takes precedence, so `testlane my-project 42 start` runs the verb. Your
command is still there as `testlane my-project 42 run start`, and `testlane doctor` warns
about the shadowing.
::

### `default_command`

```toml
default_command = "dev"
```

makes `testlane my-project 42` behave like `testlane my-project 42 run dev`. It accepts
either a verb or a configured command name.

## Hooks

Four lifecycle hooks, all optional, all templated, each executed as
`bash -c "<script>"` with the worktree as the working directory and the full
`TESTLANE_*` environment.

```toml [~/.testlane/my-project.toml]
[hooks]
post_checkout = "echo 'workspace ready: {path}'"
pre_run = "docker compose up -d"
post_sync = "pnpm install --frozen-lockfile"
pre_clean = "docker compose down"
```

| Hook | Fires | If it exits non-zero |
|---|---|---|
| `post_checkout` | After a workspace is materialized | Fails the command — `E_SETUP`, exit `6` |
| `pre_run` | Before `run`, `exec`, `shell` or `start` executes | Fails the command — `E_SETUP`, exit `6` |
| `post_sync` | After `sync` resets the worktree | Warns and continues |
| `pre_clean` | Before a workspace is removed | Warns and **skips** that removal |

::warning
Keep hooks fast and idempotent. `post_checkout` runs on every fresh workspace
and `pre_run` runs on every single `run`, `exec`, `shell` and `start`, apart
from a `start` that finds its command already running.
::

`pre_clean` is the place to release resources a workspace acquired — stop a
container, drop a scratch database — since after `clean` the directory is gone.
Because a failing `pre_clean` skips the removal, it also works as a veto:

```
warning: pre_clean hook failed for feat-login — skipping
```

Under `--dry-run`, hooks are printed as the `bash -c` line that would run, and
nothing executes.

## From the repository

A repository's `.testlane.toml` can define `[commands.*]` and `[hooks]` as
well, so its maintainers set them up once for everyone. They join your own, and
your project file wins:

| Table | How the two files merge |
|---|---|
| `[commands]` | By name. A command of yours replaces the whole repo command of that name, `cwd` and `env` included |
| `[hooks]` | Per hook name. Your `pre_run` replaces the repo's `pre_run`, and the repo's other hooks still run |
| `[env]` | By key |

So to change how the repository's `dev` runs on your machine, define your own
`[commands.dev]`. It's best to copy the repo command's `cwd` and `env` into it
if you still need them, since none of the repo command is kept:

```toml [~/.testlane/my-project.toml]
[commands.dev]
run = "pnpm dev --port {port} --open"
```

`testlane config show my-project` marks each key with where it came from. Here's
an excerpt:

```
default_command = "dev"                             # repo
commands.dev.run = "pnpm dev --port {port} --open"  # user
commands.test.run = "pnpm test"                     # repo
hooks.post_checkout = "echo ready: {path}"          # repo
```

### Trusting them first

A repo file can run anything your shell can, so its commands, hooks and setup
run only after you approve that exact content. The first time, Testlane prints
what the file would run and then the whole file:

```
my-project:.testlane.toml on origin/main would run:
  setup.run            pnpm install --frozen-lockfile
  commands.dev.run     pnpm dev --port {port}
  commands.test.run    pnpm test
  hooks.post_checkout  echo ready: {path}
--- my-project:.testlane.toml (origin/main) ---
…
---
Trust my-project:.testlane.toml? [y/N]
```

After a change upstream, it prints a diff from the version you approved and
asks again. `--yes` approves without asking. Off a terminal without `--yes`,
the command stops with exit `3`:

```
error(E_CONFIG): my-project:.testlane.toml is not trusted
hint: testlane config trust my-project
```

Until you approve, your project file works on its own, and the repository's
commands don't exist yet: `testlane my-project 42 run dev` fails with
`unknown command 'dev'`. Run `testlane config trust my-project` first.
[Ship a config with your repo](/docs/guides/ship-a-config-with-your-repo#approve-it)
covers trust in full.

## Ordering

For a `testlane my-project 42 run dev` on a fresh ref:

1. Resolve and fetch the ref, check the repository's `.testlane.toml` against
   your approval, then create the worktree.
2. `post_checkout`
3. `[setup]` — seed files, then `run` if the `cache_key` hash changed.
4. `pre_run`
5. `commands.dev.run`

Preview steps 3–5 without executing them:

```bash
testlane my-project 42 run dev --dry-run
```

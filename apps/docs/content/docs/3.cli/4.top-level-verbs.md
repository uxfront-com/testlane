Top-level verbs look after Testlane itself rather than one project: setting it up, checking your machine, editing the config and connecting your shell or an agent. Each one is the first word of the command, with no project before it:

```
testlane <verb> [args]
```

## At a glance

| Verb | What it does | `--json` |
| --- | --- | --- |
| [`setup`](#setup) | Creates the config directory and your first project file | No |
| [`projects`](#projects) | Lists the projects you've configured | Yes |
| [`doctor`](#doctor) | Checks your machine and every project file | Yes |
| [`config`](#config) | Prints, opens or checks the config files | `config validate` only |
| [`completions`](#completions) | Prints a completion script for your shell | No |
| [`mcp`](#mcp) | Serves Testlane's tools to an AI agent over MCP | No |
| [`help` and `version`](#help-and-version) | Prints the usage text or the version | No |

`setup`, `doctor`, `completions`, `mcp`, `help`, `version` and `config path` work before the config directory exists. The others stop with exit code `3` until it does.

## `setup`

`setup` gets you from a fresh install to a working project: it creates the config directory, sets the base directory for clones and workspaces in `defaults.toml` and writes your first project file.

```
testlane setup [--name <name>] [--repo <url>] [--root <dir>] [--default-branch <branch>] [--force]
```

| Flag | What it does | Default |
| --- | --- | --- |
| `--name <name>` | The project's name, and the name of its file, `<name>.toml` | Asked for |
| `--repo <url>` | The repository to clone, written as `repo` | Asked for |
| `--root <dir>` | The base directory for clones and workspaces, written to `defaults.toml` as `root` | `~/dev/testlane` |
| `--default-branch <branch>` | Written as `default_branch`, the branch `diff` and `clean --merged` compare against | None |
| `--force` | Overwrite the project file when it exists already | Off |

On a terminal, `setup` asks for each value it doesn't have a flag for, so the same command also runs in CI with flags alone. It asks for the root only while `defaults.toml` has none. A name has to match `^[a-z0-9][a-z0-9._-]*$`, and can't be `defaults` or `seeds`. We recommend passing `--default-branch`, since `diff` needs it to find where a branch started.

Add `--dry-run` to see what it would write, and `--yes` to take the defaults without asking:

```bash
testlane setup --name my-project --repo git@github.com:my-org/my-project.git --default-branch main --yes --dry-run
```

```
mkdir -p /home/you/.testlane
write /home/you/.testlane/defaults.toml
  root = "~/dev/testlane"
write /home/you/.testlane/my-project.toml
  repo = "git@github.com:my-org/my-project.git"
  default_branch = "main"
```

Without `--dry-run`, it makes the same changes and tells you what to run next:

```
→ created config dir /home/you/.testlane
→ set defaults.root = ~/dev/testlane
→ scaffolded my-project.toml
→ next: testlane my-project main
```

`setup` checks the file it wrote with the same rules every command uses, so a mistake shows up now rather than on your next command. Before it writes anything, it stops with these exit codes:

| Exit code | When |
| --- | --- |
| `2` | The name isn't valid, the repository is empty or a value is missing with no terminal to ask on |
| `3` | The project file exists already and you didn't pass `--force`, which overwrites that file alone |

When the check itself fails, `setup` exits `3` with the file already on disk, so open it with `testlane config edit <project>` and fix what the error names.

## `projects`

`projects` lists the projects in the config directory, with their repository and how many workspaces each has.

```bash
testlane projects
```

```
NAME        REPO                                  WORKSPACES  PATH-EXISTS
my-project  git@github.com:my-org/my-project.git  2           yes
```

`PATH-EXISTS` says whether Testlane has cloned the project yet. A project file that doesn't load still shows up, with `?` as its repository, and `doctor` tells you why. With `--json`, `projects` prints an array of objects with `name`, `repo`, `workspaces` and `pathExists`:

```json
[{"name":"my-project","repo":"git@github.com:my-org/my-project.git","workspaces":2,"pathExists":true}]
```

## `doctor`

`doctor` checks your machine and every project file, and tells you what to fix, so it's the first thing to run when something doesn't work.

```bash
testlane doctor
```

```
OK   git version: git 2.50.1
WARN gh (github cli): missing or unauthenticated — PR metadata & push-back wiring degrade gracefully
OK   config dir: /home/you/.testlane
OK   state dir: /home/you/.local/state/testlane
OK   project my-project: config: schema-valid
OK   project my-project: repo: bare repo at /home/you/dev/testlane/my-project/repo
OK   project my-project: fetch refspec: remote.origin.fetch configured
OK   project my-project: editor: vim (/usr/bin/vim)
```

Each line is `OK`, `WARN` or `FAIL`, then the check and what it found. `doctor` checks:

- **Your machine:** the git version, whether `gh` is installed and signed in, that the config directory is readable, that the state directory is writable, and stale lock files.
- **Each project:** that its file is valid, that its clone is a bare repository with a fetch refspec, that its editor preset is installed, commands named like a built-in verb, a `core.hooksPath` that can misbehave in worktrees, workspaces that git and Testlane's state disagree about, and that its state file reads.

`doctor` exits `1` when any check fails, and `0` when there are only warnings. With `--json`, it prints `{"ok": …, "checks": […]}`, where each check has `name`, `status` (`ok`, `warn` or `fail`) and `detail`. [Troubleshooting](/docs/guides/troubleshooting) says what to do about each `WARN` and `FAIL`.

## `config`

`config` finds, opens and checks your config files.

```
testlane config path
testlane config edit [project]
testlane config add [project]
testlane config validate [project]
```

| Subcommand | What it does |
| --- | --- |
| `path` | Prints the config directory in use. `testlane config` on its own does the same |
| `edit [project]` | Opens the project's file, or the config directory, in your editor. A project with no file yet gets a starter file first |
| `add [project]` | The same as `edit`, under the name you'd look for when adding a project |
| `validate [project]` | Checks every project file, or one, against the schema |

```bash
testlane config path
```

```
/home/you/.testlane
```

`config path` is the quickest way to see which directory wins when `--config-dir` or `$TESTLANE_CONFIG_DIR` is set, as [Global flags](/docs/cli/global-flags) explains.

`edit` opens an existing project's file in that project's `editor`, and anything else in `$VISUAL` or `$EDITOR`. Keep in mind that Testlane reads those two the way it reads `editor`, so each needs to be a preset like `vim` or a template with `{path}`, like `nano {path}`. [Editors](/docs/configuration/editors) lists the presets. With `--dry-run`, `edit` prints the editor command, and the starter file when it would write one, and changes nothing.

`validate` exits `3` when a file has a problem, and prints each one on stderr as the file, the key and what's wrong:

```bash
testlane config validate
```

```
→ all project configs valid
```

With `--json`, a check of every file prints `{"ok": …, "issues": […]}`. Naming a project that has no file exits `2`.

## `completions`

`completions` prints a completion script for `bash`, `zsh` or `fish`, so your shell completes verbs, project names and workspace slugs.

```
testlane completions <bash|zsh|fish>
```

```bash
eval "$(testlane completions bash)"
```

The script holds the project names you had when you made it, so make it again after you add a project. Another shell exits `2`:

```
error(E_USAGE): unsupported shell 'ksh'
hint: one of: bash, zsh, fish
```

[Install shell completions](/docs/guides/shell-completions) shows where to put the script for each shell.

## `mcp`

`mcp` serves Testlane's tools to an AI agent over the Model Context Protocol (MCP), so the agent calls typed tools instead of reading the CLI's output. You don't run it yourself: your MCP client starts it and talks to it over stdin and stdout.

```
testlane [--config-dir <dir>] mcp
```

```bash
claude mcp add testlane -- testlane mcp
```

`mcp` takes no arguments and exits `2` when given any, while global flags like `--config-dir <dir>` still work before or after it. The server starts even when the config directory doesn't exist yet: `doctor` still works, and every other tool returns an `E_CONFIG` error until you create it.

Each tool calls the same code as its verb and returns that verb's `--json` output. [Use Testlane from an agent](/docs/guides/use-testlane-from-an-agent#connect-over-mcp) lists the tools, what they return and the JSON config for other clients, and [ADR-003](https://github.com/uxfront-com/testlane/blob/main/docs/adrs/003-mcp-server.md) explains why we wrote the server by hand.

Note that a project named `mcp` can only be reached by its repository URL, like `testlane https://github.com/acme/mcp 42`, since the verb takes the name.

## `help` and `version`

`help` prints the grammar, every verb, the global flags and the order Testlane looks for its config directory in, and `version` prints the version.

```bash
testlane help
testlane version
```

```
testlane 2.0.0
```

Both always exit `0`. Note that they're verbs with no flag form, so `testlane help` is the way to get the usage text.

These verbs take no project argument.

## `setup`

First-run onboarding. Creates the config dir if missing, ensures `defaults.root`
so derived paths resolve, and scaffolds your first project file. It is the only
command exempt from the config-dir existence check — it is what creates the dir.

```
testlane setup [--name <name>] [--repo <url>] [--root <dir>] [--default-branch <branch>] [--force]
```

On a terminal it prompts for each field in order. Every prompt is also a flag,
so the same command runs non-interactively in CI.

| Prompt | Flag | Written to |
|---|---|---|
| Base directory for repos & worktrees | `--root` | `defaults.toml` → `root` |
| Project name | `--name` | filename `<name>.toml` |
| Repository URL | `--repo` | `<name>.toml` → `repo` |
| Default branch (blank = auto-detect) | `--default-branch` | `<name>.toml` → `default_branch` |

`--root` is skipped once `defaults.root` is set. The project name must match
`^[a-z0-9][a-z0-9._-]*$` and cannot be `defaults` or `seeds`.

Preview the writes without making them:

```bash
testlane setup \
  --config-dir ./ci-config \
  --name acme-web \
  --repo git@github.com:acme/acme-web.git \
  --default-branch main \
  --yes --dry-run
```

```
mkdir -p ./ci-config
write ci-config/defaults.toml
  root = "~/dev/testlane"
write ci-config/acme-web.toml
  repo = "git@github.com:acme/acme-web.git"
  default_branch = "main"
```

Drop `--dry-run` to apply the same plan:

```
→ created config dir ./ci-config
→ set defaults.root = ~/dev/testlane
→ scaffolded acme-web.toml
→ next: testlane acme-web main
```

Guards:

- Invalid or reserved name, or an empty repo → `E_USAGE`, nothing written.
- Project file already exists → `E_CONFIG` unless you pass `--force`, which
  overwrites only that project file.
- A required value missing on a non-TTY with no flag → `E_USAGE` naming the flag.

The freshly written file is validated with the normal loader before success is
reported, so a bad combination fails here rather than on your next command.

## `projects`

```bash
testlane projects
```

```
NAME      REPO                              WORKSPACES  PATH-EXISTS
demo-app  git@github.com:acme/demo-app.git  1           yes
```

`--json` emits an array:

```json
[{"name":"demo-app","repo":"git@github.com:acme/demo-app.git","workspaces":1,"pathExists":true}]
```

## `doctor`

Diagnoses environment and configs. Exits non-zero if any check fails.

```bash
testlane doctor
```

```
OK   git version: git 2.50.1
OK   gh (github cli): authenticated
OK   config dir: ~/.testlane
OK   state dir: ~/.local/state/testlane
OK   project demo-app: config: schema-valid
OK   project demo-app: repo: bare repo at ~/dev/testlane/demo-app/repo
OK   project demo-app: fetch refspec: remote.origin.fetch configured
```

Checks: git version, `gh` presence and auth, config-dir readability, state-dir
writability, stale locks, and per project — schema validity, the bare repo and
its fetch refspec, editor binary on `PATH`, commands that shadow built-in verbs,
`core.hooksPath`, and worktree/state drift.

See [Troubleshooting](/docs/guides/troubleshooting) for what to do with a
`WARN` or `FAIL`.

## `config`

```bash
testlane config path                 # print the config dir in use
testlane config edit [project]       # edit defaults.toml, or one project file
testlane config add [project]        # like edit; seeds a starter template if absent
testlane config validate [project]   # validate all configs, or one
```

```bash
testlane config path
```

```
~/.testlane
```

```bash
testlane config validate
```

```
→ all project configs valid
```

`config path` is the fastest way to confirm which directory is actually in use
when `TESTLANE_CONFIG_DIR` or `--config-dir` is in play. See
[Configuration overview](/docs/configuration/overview).

## `completions`

Prints a completion script for `bash`, `zsh`, or `fish` to stdout.

```bash
eval "$(testlane completions zsh)"
```

See [Install shell completions](/docs/guides/shell-completions).

## `mcp`

Serves Testlane's tools to an AI agent over the Model Context Protocol (MCP), so
the agent calls typed tools instead of parsing the CLI's output. You don't run
it yourself: your MCP client starts it and talks to it over stdin and stdout.

```bash
claude mcp add testlane -- testlane mcp
```

It takes no arguments, and exits `2` when given any. Put global flags like
`--config-dir <dir>` before `mcp`. The server starts even when the config
directory doesn't exist yet: `doctor` still works, and every other tool returns
an `E_CONFIG` error until you create it.

Each tool calls the same code as its verb and returns that verb's `--json`
output. [Use Testlane from an agent](/docs/guides/use-testlane-from-an-agent#connect-over-mcp)
lists the tools, what they return and the JSON config for other clients, and
[ADR-003](https://github.com/uxfront-com/testlane/blob/main/docs/adrs/003-mcp-server.md)
explains why the server is written by hand.

Note that a project named `mcp` can now only be reached by its repository URL,
like `testlane https://github.com/acme/mcp 42`, since the verb takes the name.

## `help` and `version`

```bash
testlane help       # the grammar, verbs, flags, and config-dir resolution order
testlane version    # the version string
```
